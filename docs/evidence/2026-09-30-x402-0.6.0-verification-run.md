# x402 Checks in 0.6.0 — A/B Against Servers Built to Lie, and the Reference

**Date:** 2026-09-30
**Wasit:** builds of the `release/0.6.0` branch (`283fa8e` for `X402-06`,
`85bba09` for `X402-07`, `c4cf2c4` for the reference run), each compared with
`@wasit-dev/cli@0.5.0` from the npm registry. Then the published
`@wasit-dev/cli@0.6.0`, run through `npx`, for registry parity.
**Targets:** Wasit's own x402 fixture; two small servers written for this run to
exhibit the gaps 0.6.0 closes; and the `simple-paywall` example with its
facilitator from [`stellar/x402-stellar`](https://github.com/stellar/x402-stellar)
at `45d735a`, the same commit as the
[2026-09-06 reference run](2026-09-06-reference-implementation-run.md). Every
target ran on our machine against Stellar testnet.
**Environment:** macOS. Registry parity on Node `v22.23.3`.

**What this is for.** 0.6.0 changes what two checks prove. `X402-06` used to
pass on any 2xx, which shows the service served the resource, not that the
payment landed; it now verifies the settlement on-chain. `X402-07` used to break
the whole transaction envelope, so a service that never checked signatures still
refused it; it now corrupts only the signature. A stricter check is only worth
having if two things hold: it fails services that the old one let through, and
it does not fail a correct implementation. The A/B runs test the first, the
reference run the second.

**Authorization.** None was needed or sought. Every target was Wasit's own code
or open-source code run on our machine. No service operated by anyone else was
tested.

## `X402-06`: settlement verified on-chain

| Target | 0.5.0 (npm) | 0.6.0 build |
|---|---|---|
| Wasit's x402 fixture, settling through a real facilitator | PASS | PASS |
| Server that answers 200 and never settles (no `PAYMENT-RESPONSE`) | PASS | **FAIL** |
| Server that answers 200 and reports a transaction that is not this payment | PASS | **FAIL** |

The two lying servers borrow the fixture's real 402 challenge and answer 200 to
any payment header without forwarding it to a facilitator, so nothing settles
through them and no funds moved in those runs. They were written for this run
and are not committed: they exist to show the gap, not as fixtures.

Output below is quoted as printed, wrapped to fit, with addresses and
transaction hashes shortened with `…`; each full hash is linked.

Against the fixture, 0.5.0 stopped at `Valid payment accepted (HTTP 200).` The
0.6.0 build follows the payment onto the chain:

```
PASS  X402-06  Signature Resubmit Accepted
      Valid payment accepted (HTTP 200) and settled on-chain for exactly the
      advertised 100000 base units of CBIELTK6…DAMA to GDPAPDZW…TDQBM, verified
      from the transfer event (tx fb98b352…5923).
```

[`fb98b352…5923`](https://stellar.expert/explorer/testnet/tx/fb98b352f0caaa25bc40e6ecf4d2fba6c519935412b8cf11e7fd6a9823835923)

Against the server that never settles, 0.5.0 passed. The 0.6.0 build:

```
FAIL  X402-06  Signature Resubmit Accepted
      Valid payment accepted (HTTP 200), but the response carried no
      PAYMENT-RESPONSE header, which the x402 v2 HTTP transport uses to report
      settlement. Whether the payment settled cannot be verified.
```

The second lying server sends a `PAYMENT-RESPONSE` that names a real, successful
testnet transaction, just not this run's payment: a 1-base-unit transfer we made
the day before to test muxed recipients
([`02f56c0a…cfe8`](https://stellar.expert/explorer/testnet/tx/02f56c0a9c1c702d504fc168013dbe4d4f1ce3bda52d7c1d432d60a6afcecfe8)).
0.5.0 passed. The 0.6.0 build holds that transaction to the advertised terms and
reports every way it misses them:

```
FAIL  X402-06  Signature Resubmit Accepted
      Settlement does not match what the target advertised — amount: advertised
      100000 base units, moved 1; recipient: advertised GDPAPDZW…TDQBM, paid
      GALVZ57V…BXUI (muxed id 42); payer: this run paid from GCWG7X3Z…TKPB2, but
      the referenced transfer came from GDHQTUA2…NAFVK (tx 02f56c0a…cfe8).
```

## `X402-07`: only the signature is forged

| Target | 0.5.0 (npm) | 0.6.0 build |
|---|---|---|
| Server that decodes the payment and never verifies the signature | PASS | **FAIL** |
| Wasit's x402 fixture, through the `x402.org` facilitator | PASS (402) | PASS (402) |

The lax server parses the transaction and accepts it without checking the
authorization signature. 0.5.0 passed it, because its corruption broke the
envelope and the server could not parse it at all, so the refusal said nothing
about signatures. The 0.6.0 build flips one byte of the signature and leaves
the rest of the transaction intact, so the server parses it and accepts it:

```
FAIL  X402-07  Invalid Signature Rejected
      A payment with a corrupted authorization signature was accepted with
      HTTP 200 — security-relevant failure.
```

Against the fixture both builds pass, but the facilitator's reason shows what
each one actually tested: `invalid_exact_stellar_payload_malformed` for 0.5.0's
broken envelope, `invalid_exact_stellar_payload_simulation_failed` for 0.6.0's
forged signature. The forged payload differs from a valid one only in the
signature bytes, so the simulation failure is the signature being refused.

## The reference implementation still passes

Run against `stellar/x402-stellar`'s `simple-paywall` and its own facilitator,
built with the repository's own `pnpm build`, with three separate accounts for
facilitator, payee and payer:

| | 0.6.0 build | 0.5.0 (npm) |
|---|---|---|
| Read-only, `X402-01`–`05` | 5/5 | — |
| Full flow, `X402-01`–`07` | **7/7** | 7/7 |

- **`X402-06`** passed on-chain:
  [`741c155b…a474`](https://stellar.expert/explorer/testnet/tx/741c155b620641a7f8845c14e7857201aed67763ea7ca087a7adf921b550a474).
  The reference server sends `PAYMENT-RESPONSE` with the hash of the settling
  transaction, so the stricter rule agrees with Stellar's own implementation.
  Had it not, the rule would have been wrong, not the reference.
- **`X402-07`** was refused for the right reason. The reference facilitator's
  simulation of the forged payment failed with `Error(Auth, InvalidAction)`,
  "failed account authentication", and it answered
  `invalid_exact_stellar_payload_simulation_failed`. With 0.5.0 the same
  facilitator logged `XdrReaderError … source buffer not entirely consumed` and
  `invalid_exact_stellar_payload_malformed`: the weakness the
  [2026-09-06 run](2026-09-06-reference-implementation-run.md) found, reproduced
  and now gone.

## Limits

- The lying and lax servers are artificial. They show that 0.6.0 detects these
  two behaviours, not that any real service has them.
- `X402-06` now requires the `PAYMENT-RESPONSE` header. A service that settles
  correctly but omits it fails, because the settlement cannot be verified from
  the outside. That is a deliberate reading of the x402 v2 HTTP transport, which
  reports settlement in that header; it is recorded in the
  [0.6.0 changelog](../../CHANGELOG.md).
- Self-hosted on our own machine, with our own keys as payer and payee.
- No third-party live service was tested.
